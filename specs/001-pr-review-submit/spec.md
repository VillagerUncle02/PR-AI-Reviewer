# Feature Specification: PR Review Submit（PR 审查结果上传）

**Feature Branch**: `001-pr-review-submit`

**Created**: 2026-08-09

**Status**: Draft

**Input**: User description: "为「PR-AI-Reviewer」创建 feature spec：特化 MCP Tool，在 AI Agent 完成 GitHub PR 代码审查后，以 GitHub App Bot 身份将审查结论通过 submit review 上传到指定 PR（整体结论作为 review body，逐条建议作为文件改动位置的 review comments）；上传成功后调用方收到明确成功结果，失败时返回明确原因；工具不生成审查内容、不持久化数据、不做 submit review 之外的其他 GitHub 操作。技术背景（供计划阶段使用）：C# / .NET LTS、官方 MCP C# SDK、Octokit / GitHub REST API、GitHub 版本管理。"

## Clarifications

### Session 2026-08-09

- Q: GitHub App 私钥与安装令牌等凭据存放在哪里？ → A: 本地 `private-key` 文件夹（仓库根目录下，登记在排除规则中，不进入版本库）。
- Q: 提交 review 的审查事件类型如何处理？ → A: 固定"仅评论"（COMMENT），不提供批准/请求修改；后续需要时再扩展。
- Q: 评论范围校验需要额外的只读 GitHub 查询吗？ → A: 评论越界校验不读取文件改动列表，以提交结果为准；但提交前必须读取一次目标 PR 状态，已合并/已关闭直接失败。
- Q: 调用方是否可以只上传整体审查结论、不带任何逐文件评论？ → A: 可以；空评论列表合法，仅上传整体结论也能成功提交。
- Q: 范围边界"不做 submit review 之外的其他 GitHub 操作"是否排除认证必需请求？ → A: 排除；安装定位与安装令牌交换属于认证的必要组成部分，边界仅约束仓库/PR 业务操作。
- Q: 在"不持久化任何数据"约束下，是否允许本地错误日志？ → A: 不允许任何日志写入；诊断信息仅通过调用结果返回，运行环境零写入。
- Q: 已合并 PR 的提交结果如何处理？ → A: 明确禁止；提交前读取目标 PR 状态，已合并或已关闭时直接返回失败、不产生新 review。
- Q: 状态读取与提交之间的 TOCTOU 竞态结果如何处理？ → A: 按平台结果如实返回；竞态下平台接受即成功，残余风险记录在需求/假设中。
- Q: v1 是否只支持单一 GitHub App 安装？ → A: 是；安装 ID 来自配置，目标仓库必须在该安装授权范围内，多安装/多租户明确为范围外。
- Q: 配置缺失或非法时 MCP server 应如何启动？ → A: 启动即失败；启动时校验必需配置，缺失或非法立即退出并给出明确错误。
- Q: GitHub API 地址（BaseUrl）是否允许配置？ → A: 不允许；固定使用生产 api.github.com，测试经接口替身或真实 GitHub 完成。
- Q: 目标 PR 为 draft 状态时是否允许提交 review？ → A: 允许；draft 不单独拒绝，仅按 state=open 且未合并判定，不额外读取 draft 字段。
- Q: "启动即失败"与 MCP stdio 按需拉起如何兼容？ → A: 保持启动即失败（非零退出码 + stderr 明确错误），由 MCP 宿主/调用方环境暴露；FR-015 不变。

### Session 2026-08-10

- Q: 运行期间私钥文件被替换成另一把有效的新私钥时，工具应该在下一次调用立即使用新私钥，还是必须重启进程后才生效？ → A: 每次调用重新读取私钥文件；删除或内容不可解析 → CREDENTIALS_INVALID；替换为有效新私钥 → 下一次调用立即生效，无需重启。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以 Bot 身份用 submit review 上传审查 (Priority: P1)

调用方 Agent 已完成对某个 PR 的代码审查，生成了整体审查结论与逐文件评论；调用工具并显式指定目标账号、目标仓库与 PR 编号。工具通过该仓库已安装的 GitHub App 认证，将整体结论作为 review 主体、逐条评论作为对应文件改动位置的 review comments 一并提交。提交成功后，PR 上出现一条带 bot 标识的已提交 review，调用方收到明确成功结果。

**Why this priority**: 这是本工具的唯一天职与核心价值——把 Agent 已完成的审查内容变成 GitHub 官方 review。没有它就没有本工具，属于 P1。

**Independent Test**: 对任意一个已安装 GitHub App 的测试仓库，向一个打开状态的测试 PR 传入有效的整体结论与若干条指向文件改动的评论；可独立验证 PR 上出现 bot 身份 review、内容与输入完全一致、评论出现在正确的文件与行位置。

**Acceptance Scenarios**:

1. **Given** 目标仓库存在且已安装 GitHub App、目标 PR 处于打开状态、载荷有效（非空整体结论 + 每条评论含文件路径、行位置与评论内容），**When** Agent 发起上传，**Then** PR 上出现一条带 bot 标识的已提交 review，整体结论与全部评论内容与传入一致。
2. **Given** 评论指定了目标 PR file change 范围内真实存在的文件路径与行位置，**When** 上传成功，**Then** 每条评论显示在对应的文件改动位置（含正确的代码侧与行）。
3. **Given** 上传成功，**When** 调用返回，**Then** 调用方收到可程序化解析的明确成功结果，无需人工查看 GitHub 页面即可确认成功。
4. **Given** 载荷仅包含非空整体结论且评论列表为空，**When** Agent 发起上传，**Then** 提交成功，PR 上出现一条包含整体结论、无逐文件评论的已提交 review。

---

### User Story 2 - 上传失败并返回明确错误 (Priority: P1)

当无法完成上传时（目标仓库/PR 不存在、GitHub App 未安装、权限不足、PR 已关闭或已合并、载荷无效、凭据缺失或过期、GitHub API 网络错误或限流、部分评论无法提交等），工具必须向调用方返回明确、可操作的失败原因，不得静默吞掉错误，也不得产生不确定的半成功状态。

**Why this priority**: 调用方是 AI Agent，依赖确定性的成功/失败信号决定下一步；模糊或静默失败会导致重复上传或审查缺失。该行为与"失败透明"原则一致，属于 P1。

**Independent Test**: 分别对不存在的 PR、已关闭的 PR、缺少必要字段的载荷发起上传；可独立验证调用方每次均收到明确失败原因，且 GitHub 上未产生任何新 review、未发出任何提交请求。

**Acceptance Scenarios**:

1. **Given** 目标 PR 不存在、已合并或已关闭，**When** Agent 发起上传，**Then** 调用方收到能区分"目标不可提交"的明确失败原因，且目标 PR 上无任何新 review 产生。
2. **Given** 载荷缺少必要字段（如整体结论为空、评论缺文件路径或行位置）或结构无效，**When** Agent 发起上传，**Then** 调用方收到格式错误提示，且工具未向 GitHub 发出任何提交。
3. **Given** 任一失败场景发生，**When** 调用结束，**Then** 调用方收到的结果必须为明确失败（含原因），不存在"部分成功"或静默无结果。
4. **Given** 必需配置缺失或非法（如 App ID、安装 ID、私钥缺失/不可解析），**When** 启动 MCP server，**Then** 启动即失败（非零退出码 + stderr 明确错误），不进入任何工具调用。

---

### User Story 3 - 重复提交由调用方控制 (Priority: P2)

工具不做隐式重试或自动补偿；同一次调用失败后，由调用方修正载荷或条件后再次发起上传。调用方可在任意时刻发起新的上传尝试。

**Why this priority**: 保持行为确定性，避免工具在 Agent 不知情的情况下重复提交或产生多余 review；重试策略属于调用方编排职责，属 P2。

**Independent Test**: 制造一次失败上传，观察工具不会自行发起任何后续 GitHub 请求；随后由调用方再次发起有效上传，可成功产生一条新的 review。

**Acceptance Scenarios**:

1. **Given** 一次上传失败，**When** 经过任意等待时间，**Then** 工具不会自行重试或自动补偿，GitHub 上不会出现由工具自动发起的额外请求或 review。
2. **Given** 调用方修正载荷或条件后再次发起上传，**When** 载荷与目标条件有效，**Then** 上传成功并返回明确成功结果。

---

### Edge Cases

- 目标账号或仓库不存在、拼写错误或无访问权限：返回明确失败，不产生任何新 review。
- GitHub App 未安装到目标仓库、目标仓库不在所配置安装的授权范围内，或安装已撤销：返回明确失败，说明 App 未安装/无权限。
- 必需配置缺失或非法（App ID、安装 ID、私钥缺失或不可解析等）：启动即失败，返回明确配置错误。
- 目标 PR 为 draft（草稿）状态：不单独拒绝，按 state=open 且未合并处理；draft 字段不纳入状态读取。
- PR 编号不存在、已合并或已关闭：返回明确失败，不提交、不产生新 review。
- 载荷缺少必要字段或结构无效（整体结论为空、评论缺文件路径或行位置等）：在向 GitHub 发起提交前即拒绝并返回格式错误。
- 整体结论或评论内容为纯空白（去除首尾空白后为空）：视为载荷无效，返回格式错误且不向 GitHub 发起提交。
- owner/repo/path 等字符串字段不设本地上限；格式规范性与存在性以 GitHub 判定为准（对应目标不存在/载荷被拒类失败）。
- 评论指向的文件或行不在目标 PR 的 file change 范围内：整次调用判为失败并返回明确原因；不得忽略该评论而部分提交；越界判定以提交结果为准，工具不读取文件改动列表做前置校验（FR-014）。
- 凭据缺失、过期或无效：返回明确失败，且不向 GitHub 发起任何操作。
- 启动后运行期间私钥被删除或替换为不可解析内容：调用时读取/解析失败，按凭据无效类（CREDENTIALS_INVALID）明确失败返回，由调用方检查配置后重试；替换为有效新私钥时，下一次调用按新私钥生效，无需重启（2026-08-10 澄清）。
- 目标 PR 无文件改动（空 diff）：仅整体结论可成功提交；若包含评论，评论无法定位到改动位置，提交整体失败并返回明确原因（以平台结果为准）。
- 安装后 App 权限在调用期间被移除或降级（认证通过后提交阶段 403）：按 App 未安装/无权限类明确失败返回。
- GitHub API 网络错误、超时或限流：返回明确失败原因；由调用方决定是否重试。
- 提交过程中部分评论失败：整次调用判为整体失败并报告；调用方不得收到成功或部分成功信号（整体原子性的实现方式以计划阶段确定）。
- 提交请求已发出但响应超时：返回明确网络失败原因，并提示调用方该 review 可能已创建；工具不自动重试，由调用方核验并去重（工具不保证幂等）。
- 状态读取与提交之间 PR 被关闭或合并（竞态）：若平台仍接受提交，工具按平台结果如实返回成功；该残余风险已作为假设接受。
- 认证成功后提交阶段收到 401（令牌中途失效）：返回凭据无效类明确失败，由调用方检查凭据后重试。
- 状态读取通过后目标 PR 被删除或仓库被转移（提交阶段 404）：按"目标不存在"返回明确失败；属于已接受的竞态风险。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：工具 MUST 仅向调用方暴露"提交 PR review"一个操作；除 GitHub App 认证所需的必要请求（安装定位、安装令牌交换）与提交前的目标 PR 状态读取外，每次调用不得触发任何其他 GitHub 操作（不读取 PR 文件改动列表等业务数据、不做任何其他变更）。
- **FR-002**：每次调用 MUST 显式指定并仅使用目标账号、目标仓库与 PR 编号；MUST NOT 通过默认值、推断、环境上下文或通配符选择目标。目标账号与目标仓库 MUST 为 trim 后非空的必填字符串，纯空白视为缺失，按格式错误在本地拒绝，不向 GitHub 发起请求；PR 编号 MUST 为大于等于 1 的整数。
- **FR-003**：工具 MUST 校验载荷完整性：整体结论 MUST 为去除首尾空白（Unicode 空白字符，不含零宽空格等格式字符）后的非空文本；评论列表可为空，若提供评论则每条评论 MUST 包含文件路径、行位置与去除首尾空白后非空的评论内容。去除首尾空白仅用于有效性判断，提交时保持调用方原始内容；缺失任一必需字段或结构无效时，MUST 返回格式错误且不向 GitHub 发起任何提交。
- **FR-004**：工具 MUST 在提交前读取目标 PR 状态（仅 state 与 merged 字段）：仅当 PR 存在、state 为 open 且未合并时才可继续提交（draft 状态不单独拒绝）；PR 不存在、已合并或已关闭时 MUST 直接返回明确失败，且不向 GitHub 发起 review 提交。
- **FR-005**：工具 MUST 将传入的整体结论作为 review 主体、将逐条评论作为对应文件位置的 review comments 一并提交；MUST NOT 修改、增删或重新生成审查内容。
- **FR-006**：工具 MUST 通过目标仓库已安装的 GitHub App 认证，并以该 App 的 bot 身份完成提交；MUST NOT 以人类账号身份代发、隐藏或伪造身份。
- **FR-007**：提交成功时，工具 MUST 返回明确成功结果；该结果 MUST 可被调用方程序化解析，并对应 GitHub 上一条带 bot 标识、包含整体结论与全部评论的已提交 review。
- **FR-008**：当目标不存在/无权限、App 未安装、PR 不存在/已关闭/已合并、载荷无效、凭据缺失/过期/无效、网络错误或限流、部分评论失败等任何失败发生时，工具 MUST 返回明确、可操作的失败原因；MUST NOT 静默吞错、返回成功或产生不确定状态。
- **FR-009**：若提交过程中出现部分评论失败，工具 MUST 将整次调用判为整体失败并报告；MUST NOT 向调用方返回部分成功状态。
- **FR-010**：工具 MUST NOT 隐式重试或自动补偿；一次失败后仅可由调用方重新发起上传。
- **FR-011**：工具 MUST NOT 持久化、缓存或存储任何数据（含错误日志）；每次调用 MUST 为无状态处理，诊断信息仅通过调用结果返回，且 MUST NOT 包含令牌、私钥等敏感内容（含透传的 GitHub 错误详情）。运行期除 MCP 协议与调用结果输出外，不得产生其他 stdout/stderr 输出。
- **FR-012**：工具 MUST 仅使用本地 `private-key` 文件夹（仓库根目录下，受保护位置）中的 GitHub App 凭据；该文件夹 MUST 登记在 .gitignore（或等效排除规则）中，MUST NOT 出现在任何版本库内容中，并 MUST 使用短期令牌及时失效。
- **FR-013**：工具 MUST 以"仅评论"（COMMENT）事件提交 review；MUST NOT 使用"批准"或"请求修改"事件，也不得由调用方指定审查事件类型。
- **FR-014**：工具 MUST NOT 读取目标 PR 的文件改动列表做前置校验；状态读取响应中附带的元数据不用于任何校验；评论是否在 file change 范围内以提交结果为准，任何评论越界时提交 MUST 整体失败并返回明确原因。
- **FR-015**：工具 MUST 在启动时校验必需配置（App ID 或安装 ID 缺失/非正整数、私钥路径不存在或不可读、私钥无法解析为 RSA 密钥等）：配置缺失或非法时 MUST 启动即失败（非零退出码 + stderr 明确错误，由 MCP 宿主/调用方环境暴露），不得以"可启动但不可用"的状态运行；stderr 输出属进程输出，不构成 FR-011 的持久化写入。启动校验仅本地进行，不发网络请求、不做令牌交换预检。
- **FR-016**：工具 MUST 固定使用 GitHub 生产 API 地址（api.github.com），MUST NOT 提供可配置的 API 地址覆盖项，且 MUST 启用 TLS 证书校验、MUST NOT 禁用。

### Key Entities *(include if feature involves data)*

- **上传请求（Review Submit Request）**：单次调用的全部输入，包含目标账号、目标仓库、PR 编号、整体结论与逐文件评论列表。
- **整体结论（Review Body）**：调用方生成的非空审查总结文本，上传后作为 review 主体展示。
- **逐文件评论（Review Comment）**：调用方生成的单条审查意见，包含文件路径、行位置（含代码侧）与评论内容。
- **目标 PR（Target Pull Request）**：由账号+仓库+编号唯一定位，须处于打开状态且位于该 GitHub App 安装与授权范围内。
- **已提交 Review（Submitted Review）**：GitHub 平台上的产物，带 bot 标识，包含整体结论与各文件位置的评论。
- **调用结果（Call Result）**：每次调用返回的结构化结果，为明确成功或明确失败（含原因），供调用方决策。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：100% 的有效上传请求在目标 PR 上生成一条已提交 review，整体结论与全部评论内容与调用方输入语义一致（内容原样提交、无增删改；不承诺平台渲染层的字节级一致）。
- **SC-002**：100% 的逐文件评论显示在输入所指定的文件与行位置。
- **SC-003**：100% 的已提交 review 被 GitHub 标记为 bot 身份，无任何冒充人类身份的提交。
- **SC-004**：100% 的失败调用向调用方返回明确、可操作的失败原因；失败调用中 0 次静默吞错。
- **SC-005**：对目标不存在、App 未安装、PR 不存在/已关闭/已合并或载荷无效的调用，0 次产生新 review（0 误提交）；竞态下平台接受并成功创建的 review 不视为误提交。
- **SC-006**：调用结果中 0% 出现半成功状态；每次调用要么整体成功，要么整体失败。
- **SC-007**：任意调用结束后，工具运行环境中 0 条数据被持久化（含日志、缓存等任何写入）。
- **SC-008**：在 GitHub 平台可用且网络正常的前提下，单次上传从调用到返回明确结果在 30 秒内完成。
- **SC-009**：100% 的成功/失败结果可被调用方程序化解析，无需人工查看 GitHub 页面即可作出下一步决策。

## Assumptions

- 唯一使用者是调用方 Agent；工具以 MCP Tool 形式接受结构化的上传调用，无图形界面或人工交互。
- 调用方的典型工作流为"审查 → 修复 → 再审查"循环直至通过后上传最终结论；本工具只负责循环结束后的上传，不参与循环内的审查或修复。
- 每次调用显式指定目标账号、仓库与 PR 编号；不存在任何选择或推导目标账号/仓库的机制。
- 工具不保证幂等：每次调用独立生成一条 review，重复或并发调用可能产生多条 review；去重与并发控制由调用方负责。
- 可观测性通过结构化调用结果实现；工具不写日志、不落盘，运行环境零持久化写入。
- 提交前会读取一次目标 PR 状态以判定可提交性（PR 不存在/已合并/已关闭直接失败）；除此之外工具不读取任何 PR 业务数据。
- 状态读取与提交之间存在竞态窗口（TOCTOU）：若 PR 在窗口内被合并/关闭而平台仍接受提交（已合并场景），工具按平台结果如实返回；该残余风险已接受。
- 目标 PR 的状态字段（state/merged）语义以 GitHub 返回为准；状态读取仅消费这两个字段。
- MCP 传输层错误（工具调用无法到达、参数序列化失败等）不属于工具返回结果的契约范围，由调用方与 MCP 宿主处理。
- 审查内容（整体结论与逐条评论）按 UTF-8 原样提交，工具不做编码转换或内容规范化。
- GitHub API 地址固定为生产环境（api.github.com），不支持配置覆盖；测试通过接口替身或真实 GitHub 完成。
- 私钥在启动时仅校验存在与可解析性；每次调用按需重新读取并生成短期令牌，不做缓存，与无状态约束一致。
- 同一进程内并发多次调用相互独立：每次调用各自完成认证与提交，不共享可变状态或复用令牌。
- 目标账号类型（用户级或组织级仓库）不做区分，统一按该 GitHub App 安装的授权范围判定。
- 私钥轮换无需重启：每次调用重新读取私钥文件，替换为有效新私钥后下一次调用即生效，旧私钥随即失效；删除或替换为不可解析内容按 CREDENTIALS_INVALID 失败（2026-08-10 澄清；配置本身仍启动时固化，运行期环境变量变更不生效）。
- 审查内容（整体结论与逐条评论）完全由调用方生成；工具只负责提交，不分析代码、不生成或修改任何审查意见。
- 目标仓库已安装并授权该 GitHub App；未安装或授权失效时按失败路径处理并返回明确原因。
- v1 仅支持单一 GitHub App 安装：installation_id 来自配置，目标仓库必须位于该安装授权范围内；多安装/多租户（按仓库解析安装）明确为范围外。
- GitHub App 私钥与安装令牌等凭据保存在仓库根目录下的 `private-key` 文件夹（本地受保护位置），并登记在 .gitignore（或等效排除规则）中，绝不进入版本库；令牌为短期有效并及时失效。
- 通过 GitHub App 执行的所有程序化操作，GitHub 平台会标记为 bot 操作；工具不得伪造、隐藏或冒充人类身份。
- 技术背景（仅供计划阶段参考，不构成功能需求或验收约束）：C# / .NET LTS、官方 MCP C# SDK、Octokit / GitHub REST API、GitHub 版本管理。
- 本功能为 v1 唯一功能，MVP 即完整交付；工具只执行"提交 review"一种操作，范围外事项（内容生成、持久化、CI/CD、通知等）一律不做。
- 部分评论失败时的整体原子性以计划阶段可实现性为准；无论实现细节如何，调用方可观察结果必须为整体成功或整体失败，不得出现半成功信号。
- SC-008 的时间指标以 GitHub 平台可用且网络正常为前提。
